# v4 기반 BLE 마우스 전송 수정

## 확인한 상태와 한계

사용자는 양쪽 v4에서 USB 출력은 정상, PC BLE 출력에서는 지연이 발생한다고
확인했습니다. Windows의 `BluetoothLEDevice.GetConnectionParameters()`로 읽은
실제 Toucan 연결은 15ms 간격, peripheral latency 30, 양방향 2M PHY였습니다.
이는 무선 연결의 설정값이며 커서 지연 시간을 직접 측정한 결과는 아닙니다.
latency 30이라는 사실만으로 모든 지연의 원인을 확정하지 않습니다.

## 왼쪽 변경

PC 연결의 선호 간격을 15ms, peripheral latency를 0으로 요청합니다.
마우스 사용 중 실제 연결 정보도 확인하고, latency가 0이 아니거나 간격이 15ms보다
길면 `bt_conn_le_param_update()`로 갱신을 요청합니다. 재요청은 최대 15초에 한 번이며,
PC가 수락했는지는 연결값을 다시 읽어 검증해야 합니다. PC가 7.5ms만을 요구한 이전
설정을 거절했는지는 확인되지 않았으므로 그런 원인으로 단정하지 않습니다.
좌우 연결의 peripheral latency도 0으로 요청합니다.

ZMK v0.3 기본 마우스 전송 큐에 이동 보고가 누적되면 입력 스레드가 큐 공간을
기다릴 수 있습니다. 마우스 BLE 보고를 별도 스레드로 전달하고, 같은 버튼 상태의
연속 이동은 하나의 대기 보고로 합칩니다. BLE 스택에는 마우스 보고를 한 건씩 넣습니다.
누름/해제 경계를 넘어서 합치지 않아 정상적인 더블클릭의 버튼 변화 순서를 보존합니다.
USB 출력 및 키보드 HID 전송은 기존 경로를 유지합니다.

이전 v6/v7의 합산 큐에는 최신 이동의 시각을 갱신하지 않아, 소비가 느리면 최근 이동까지
버리는 결함이 있었습니다. 움직임이 계속 들어오면 합산 이동의 시각을 갱신하고,
움직임 없는 보고는 시각을 연장하지 않습니다. 입력이 끊긴 뒤 40ms 넘은 대기 이동은
버리되 버튼 변화는 유지합니다. 40ms는 전송 전에 기다리는 시간이 아닙니다.

## 검증 및 적용

125Hz로 8초 동안 합계 2000의 이동을 넣은 코드 재현에서, 기존 큐는 소비 간격
64/128ms일 때 500만 전달했고 수정한 큐는 2000을 모두 전달했습니다.
10분간의 지속 입력, 느린 소비, 버튼 변화 순서, 오래된 이동 제거, 재시도 및
해제 복구 검사도 수행합니다. 이는 실제 무선 장치에서 측정한 성능 수치가 아닙니다.

양쪽 v4 사용자에게 왼쪽은 BLE 수정본, 오른쪽은 드래그 거리 조정본을 제공합니다.
오른쪽의 센서/전송 형식은 v4 그대로이며, v5 이후의 이동 억제 타이머나 X/Y 묶음
전송은 추가하지 않았습니다. 아이콘 위치와 모양도 변경하지 않았습니다.
실기기 확인 전에는 BLE 지연이 해결됐다고 단정하지 않습니다.
